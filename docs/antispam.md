# Антиспам: этапы 1–7

Реализованы ручная подготовка данных, локальная модель, LEARNING, SHADOW и защищённый ACTIVE.
Без модели действует COLD_START. По умолчанию автоматическое удаление выключено.
В ACTIVE оно доступно только после отдельной проверки качества и команды администратора;
автоматических банов и мутов нет. Модуль не обращается к Gemini или другим AI API.
Существующие развлекательные команды работают независимо от антиспама.
Разделы ниже описывают последовательные этапы; актуальные условия удаления приведены в этапе 7.

## Включение

Для этого этапа используйте **Node 24+**: `npm install`, затем `node src/index.ts`.
Хранилище использует встроенный `node:sqlite`, отдельный сервер БД не нужен.
На Bun новый модуль не проверен; прежний запуск без антиспама сохранён благодаря
отложенной загрузке SQLite. Тесты проверены на Node 25.7.0.

В `.env` задайте:

```dotenv
ANTISPAM_CHAT_IDS=-1001234567890
ANTISPAM_DATABASE_PATH=data/antispam.sqlite
TRAINING_DATA_RETENTION_DAYS=180
```

ID нескольких групп разделяются запятыми. Пустой список полностью отключает модуль.
Боту нужны права администратора для проверки участников и право удаления сообщений
для кнопки «Удалить / Spam». Бот должен получать сообщения группы; настройки получения
сообщений описаны в основном README. Реальную группу для проверки автоматически не подключаем.

## Разметка

- `/spam review` ответом на текст или подпись — создать карточку проверки в этой же группе.
- `/spam rewiev` — поддерживается как алиас `/spam review`.
- **Удалить / Spam** — человеческая метка `ADMIN_CONFIRMED` и попытка удалить сообщение.
- **Оставить / Normal** — метка `ADMIN_REJECTED`, сообщение сохраняется.
- **Пропустить** — закрыть проверку без метки.
- `/spam undo <id>` — удалить метку из обучающей выборки, сохранив аудит решения.
  Для новой разметки после отмены снова вызовите `/spam review` ответом на исходное сообщение.
  Telegram-сообщение после удаления не восстанавливается.
- `/spam status`, `/spam stats` — режим, объём данных, число уникальных меток и ожидающих проверок.
- `/spam train` — обучить новую модель группы в отдельном worker. Результат придёт отдельным сообщением.

Без модели карточки создаёт администратор вручную. После успешного `/spam train`
бот также сам предлагает подозрительные сообщения.
Размечать нужно и обычные сообщения, иначе не появится второй класс для будущего обучения.
Проверки истекают через 30 минут. Старые кнопки больше не принимают решения.

Авторство решений проверяется через `getChatMember` при каждой команде и нажатии,
без кэша прав. Анонимные администраторы не могут размечать от имени группы.
Кнопка привязана к конкретной карточке и группе. Первое решение фиксируется транзакцией;
повторное нажатие не создаёт метку и не повторяет удаление. Администраторы, боты и сообщения
от имени каналов защищены от удаления этим модулем.

## Начальная база

Локальный доверенный оператор может импортировать JSON:

```json
[
  { "text": "пример рекламного сообщения", "label": "spam" },
  { "text": "всем доброе утро", "label": "normal" }
]
```

```bash
node src/antispam/import.ts -1001234567890 ./bootstrap.json
```

Группа должна быть в `ANTISPAM_CHAT_IDS`. Токен для импорта не нужен. Лимит файла — 10 MiB,
число примеров — 10000. Весь импорт валидируется и записывается транзакцией.
Повторный импорт не увеличивает выборку; конфликт меток отменяет весь импорт.
CSV и загрузка файлов через Telegram отложены.

## Архитектура и данные

- `src/antispam/normalizer.ts`: неизменный оригинал, NFKC, нижний регистр, пробелы,
  URL/username/длинные числа как токены; отдельно версия с сокращением повторов и SHA-256.
- `src/antispam/store.ts`: SQLite с версией схемы, внешними ключами, WAL и транзакциями.
  Таблицы `messages`, `labels`, `moderation_cases`, `feedback_audit` и представление `training_dataset`.
- `src/antispam/telegram.ts`: получение сообщений, актуальная проверка прав, ручные карточки,
  удаление по явному решению администратора и очистка старых записей.
- `src/antispam/import.ts`: отдельная локальная команда импорта.
- `src/antispam/model.ts`: контракт JSON-модели, char TF-IDF и оценка сообщения из памяти.
- `src/antispam/training.ts`, `trainWorker.ts`: разделение выборки, обучение и validation в worker.
- `src/antispam/learning.ts`: запуск worker, проверка снимка данных и атомарная активация модели.
- `src/antispam/decision.ts`: отдельный DecisionEngine с результатами только ALLOW / ASK_ADMIN.

Сохраняются тексты и подписи полученных сообщений выбранных групп, ID, username, время,
entities, сведения о пересылке, ответе и наличии медиа. Сервисные сообщения без текста и
подписи пропускаются. Медиафайлы не скачиваются. Сообщения остаются без метки, пока человек
их не разметит. Отсутствие записи в `labels` означает `UNLABELED`.

`training_dataset` допускает только человеческие метки и `BOOTSTRAP`. `AUTO_PREDICTION`
не включается в обучение. Дубликаты объединяются по группе и хешу нормализованного текста.
Противоречивые метки исключают всю группу дубликатов из обучения до исправления разметки.
Скрытые URL сохраняются в entities и используются в числовых признаках моделей формата 2.

Сообщения сохраняются по версиям. Событие `edited_message` закрывает ожидающую проверку
старой версии, сохраняет новый снимок и повторно запускает модель. Редактирование текста,
подписи и скрытой ссылки учитывается. `/spam review` ответом на актуальное отредактированное
сообщение создаёт проверку новой версии, даже если старый текст уже был помечен Normal.
Карточка показывает номер версии и скрытые ссылки. Старые кнопки больше не могут разметить
или удалить новую версию. Метки старого текста остаются привязаны только к старому снимку.

Миграция 2 → 3 добавляет `source_message_id`, `revision` и `last_update_id`.
Архивный снимок сохраняет исходный Telegram ID в `source_message_id`; поле
`telegram_message_id` занято только у актуальной версии. Каждая версия имеет отдельные
метку, прогноз и проверку без перезаписи истории. Bootstrap-примеры не изменяются.
Счётчик сообщений в stats учитывает сохранённые снимки.

Редактирования упорядочиваются по `edit_date`, при совпадении секунды — по `update_id`.
Повторная доставка не создаёт дубликаты; запоздалое событие или устаревший ответ не откатывает
текущую версию. Если порядок двух разных снимков в одной секунде неизвестен, ревью отклоняется
до получения актуального события. Удаление подписи также закрывает старую проверку;
пустая версия не отправляется на разметку. Изменённые команды не исполняются как команды бота.

Получение `message`, `edited_message` и `callback_query` явно включено в polling.
Telegram присылает [edited_message](https://core.telegram.org/bots/api#update) для сообщений,
известных боту: нужны доступ к группе и получение её сообщений. Пропущенные изменения
произвольного старого сообщения нельзя запросить через этот механизм задним числом.
Также нельзя проверить правку, событие о которой ещё не доставлено боту, перед удалением.
Отсутствие модели оставляет ручное ревью; наличие события само по себе не означает спам.
Лимиты автоматических карточек действуют и для редактирований. После нового обучения модель
учитывает число скрытых URL и их тип (Telegram/внешние). Конкретный адрес домена не является
отдельным признаком: замена одного внешнего URL другим может не изменить оценку.

Ошибка удаления не отменяет человеческую метку: карточка сообщает об ошибке, БД хранит
`deletion_status`. Сбой процесса между фиксацией решения и запросом в Telegram оставляет
`PENDING` в этом поле; автоматического повтора удаления нет. Гарантированной атомарности
между SQLite и Telegram нет. После такого сбоя удаление проверяется вручную.

Очистка выполняется при запуске и каждую минуту: сообщения старше заданного срока вместе
с метками, карточками в БД и аудитом удаляются каскадно. Это логическое удаление записей,
а не гарантированное стирание байтов на диске. Резервные копии и сообщения-карточки в Telegram
этой настройкой не очищаются. БД, WAL и SHM исключены из Git; ограничьте доступ к файлам
на сервере, поскольку в них находится переписка. Обычные логи модуля не содержат текстов.

## Реализованные этапы

1. **Сделано:** локальная база, сбор, нормализация, ручная разметка, отмена, JSON bootstrap.
2. **Сделано:** char TF-IDF 3–5 + Logistic Regression, отдельный worker, validation без
   пересечения нормализованных дубликатов, DecisionEngine и предложения администраторам.
   Миграция схемы 1 → 2 добавляет `predictions`, `model_versions` и связь проверок с прогнозами.
3. **Сделано:** Word TF-IDF 1–2 и 15 числовых признаков, совместимость старых моделей.
4. **Сделано:** Markov spam/normal как дополнительный сигнал, отдельные оценки в карточках и БД.
5. **Сделано:** Similarity, кампании и поведение пользователей.
6. **Сделано:** SHADOW, метрики, версии модели, калибровка порога и rollback.
7. **Сделано:** ACTIVE после проверки precision/FPR и ручного включения администратором.

Тесты: `npm test`; типы: `npm run typecheck`; сборка: `npm run build`.
Интеграционные сценарии используют поддельный Telegram API и настоящую локальную SQLite.

## Обучение и применение модели (этапы 2–3)

Новые зависимости не нужны, Python не используется. Реализованы разреженный char TF-IDF
и бинарная Logistic Regression на TypeScript. TF: `1 + ln(count)`, IDF:
`ln((N + 1) / (DF + 1)) + 1`, нормирование L2. Это стандартная схема
[sublinear TF-IDF](https://github.com/scikit-learn/scikit-learn/blob/main/doc/modules/feature_extraction.rst).
Символьные n-граммы — 3–5 Unicode code points, `min_df=2`, максимум 30000 признаков,
отбор по document frequency. Нормализованный текст сохраняет повторы; сокращённая версия
используется только для группировки похожих дубликатов перед разбиением.

LR минимизирует `(sum(balanced_weight * logistic_loss) + 0.5 * ||w||²) / N`, bias без
штрафа. Batch gradient descent, шаг 1, максимум 2000 итераций, критерий остановки —
максимальная абсолютная компонента градиента меньше 0.0001. Несходимость отменяет
обновление модели. Это собственная реализация, не обёртка scikit-learn; веса классов
соответствуют формуле [balanced](https://scikit-learn.org/1.8/modules/generated/sklearn.linear_model.LogisticRegression.html).

Для запуска нужно минимум **50 уникальных spam и 200 normal** после удаления конфликтов
и объединения вариантов с сокращёнными повторами. `/spam stats` показывает счётчики SQL,
поэтому итоговое количество для обучения может оказаться меньше. При нехватке данных
`/spam train` сообщает, сколько не хватает. Максимум — 10000 уникальных примеров.

Обучение запускает только администратор командой `/spam train` или локальный оператор:

```bash
node src/antispam/train.ts -1001234567890
# после npm run build:
node dist/antispam/train.js -1001234567890
```

Разделение — детерминированное стратифицированное 80/20 по отсортированным хешам.
Одинаковые нормализованные тексты и тексты с одинаковой сокращённой версией не пересекают
границу train/validation. Более сложные перефразирования и кампании пока не группируются.
TF-IDF обучается только на train. Для опубликованной модели сохраняются именно эти веса:
дополнительного fit на всей базе после validation нет.

В `/spam stats` выводятся precision, recall, F1 и FPR на validation при пороге 0.60.
Метрики на маленькой базе нестабильны, а score не откалиброван; они не разрешают автоудаление.
Порог качества для ACTIVE относится к будущим этапам. На этом этапе завершённая модель
включает экспериментальные предложения независимо от значений validation-метрик.

В worker действует лимит V8 heap 256 MiB и таймаут 120 секунд (это не жёсткий предел RSS
всего процесса). Только одно обучение одновременно на экземпляр бота. Во время обучения
прежняя модель продолжает работать; очередь сообщений группы не ждёт завершения worker.
Если метки изменились за время обучения, новая модель отклоняется. Переобучение пока ручное,
автоматического запуска по таймеру нет.

Модель группы хранится как проверяемый JSON в `model_versions`, без pickle или исполняемых
артефактов. JSON содержит словарь, IDF, веса, bias, версию нормализатора, метрики, хеши train
и validation и число итераций. Смена активной версии — одна SQLite-транзакция. Ошибка
обучения оставляет прежнюю версию. При запуске модель загружается в RAM; следующие сообщения
не перечитывают JSON, пока версия не изменится. Модель, опубликованная локальной CLI,
подхватывается работающим ботом при следующем обращении без перезапуска.

Score >= 0.60 даёт ASK_ADMIN, меньший score — ALLOW. Даже 1.0 не удаляет сообщение.
Пустой текст получает отсутствие оценки и ALLOW. Старая char-модель также воздерживается
при отсутствии известных n-грамм; новый формат может оценить такой текст по числовым признакам.
Для администраторов, ботов, сообщений от имени каналов и slash-команд автоматические карточки
не создаются; невозможность проверить права автора также подавляет карточку.
Карточки остаются в исходной группе, нажимать их могут только её текущие администраторы.

Не больше одной автоматической карточки в минуту на группу и не больше 20 ожидающих
проверок. Ограниченные прогнозы всё равно сохраняются в `predictions` с причиной
`review_rate_limited`, но не ставятся в отложенную очередь. Повторное получение того же
сообщения не создаёт новую карточку. При ошибке отправки карточки можно вручную вызвать
`/spam review` ответом на исходное сообщение. При рестарте фоновой рассылки старых прогнозов нет.

Сами прогнозы никогда не создают метки. Нужны прежние кнопки Spam / Normal. Undo исключает
метку из следующего обучения; для обновления действующих весов нужно снова `/spam train`.
Прогнозы удаляются вместе с исходным сообщением по retention. Версии моделей автоматически
не очищаются: они содержат фрагменты текста в словаре; храните БД и её резервные копии
с теми же ограничениями доступа, что и переписку. Rollback-интерфейс и очистка старых моделей
относятся к следующему этапу управления версиями.

## Word TF-IDF и числовые признаки

Word/numeric-признаки появились в JSON-моделях **формата 2** и сохраняются в формате 3. Прежние модели формата 1 продолжают
работать с прежним расчётом char-признаков до переобучения. `/spam stats` показывает набор
признаков активной модели. Python и новые зависимости не нужны, миграция SQLite не требуется.

Word TF-IDF использует отдельный словарь: слова и пары соседних слов, включая односимвольные
русские слова и токены `<URL>`, `<USERNAME>`, `<NUMBER>`. Максимум 10000 признаков, `min_df=2`,
sublinear TF, smoothed IDF, нормирование L2. Словарь и IDF обоих текстовых блоков строятся
строго на train; validation не влияет на отбор признаков.

`features.ts` извлекает из исходного текста 15 признаков: длину, число слов, долю уникальных
слов, доли заглавных букв/цифр/спецсимволов, число и долю emoji, число всех/Telegram/внешних
URL, число упоминаний, наличие похожего на телефон числа, число переносов и долю символов
в повторах длиной от трёх. Длины и доли считаются по Unicode code points. Emoji — приближённый
подсчёт pictographic/flag code points, не число визуальных grapheme clusters; телефон — эвристика.

Для URL и упоминаний используются также entities/caption_entities с UTF-16 offsets.
Видимая ссылка, найденная и регулярным выражением, и Telegram entity, не считается дважды.
Скрытые `text_link` учитываются, домены Telegram проверяются по точному hostname. Для bootstrap
без entities доступны только признаки видимого текста. Внешние страницы не запрашиваются.

Обучающая выборка берёт raw_text и metadata из одного реально размеченного снимка — первого
по ID среди доверенных дубликатов. Метаданные не смешиваются между сообщениями. Сокращённая
версия текста по-прежнему применяется для группировки дубликатов, исходная — для числовых
признаков. Старые данные уже содержат необходимый исходный текст.

Числовые счётчики преобразуются фиксированным `log1p(value)/log1p(cap)` с отсечением до 1,
доли/флаги ограничиваются диапазоном 0–1. Caps: длина 16384, слова 4096, emoji/переносы 256,
ссылки/упоминания 32. Это константы формата, а не статистики validation. Каждый текстовый
блок умножается на `1/sqrt(3)`, числовой блок — на `1/sqrt(3*15)`. Норма объединённой строки
не превышает 1, что сохраняет ограничение шага оптимизатора. Новая модель хранит оба словаря,
оба набора IDF и упорядоченные имена числовых признаков; несовместимый артефакт отклоняется.

Общий вектор используется одной и той же функцией при обучении, validation и inference.
Пороги, ручное подтверждение и запрет автоматических наказаний не изменены. Факт наличия
ссылки или конкретного слова сам по себе не вызывает удаление.

## Markov: этап 4

Новое `/spam train` создаёт артефакт **формата 3** с двумя символьными Markov-моделями:
spam и normal. Всё выполняется на TypeScript в прежнем worker. Старые форматы 1/2 сохраняют
прежнее поведение до переобучения. Порог данных остаётся 50 spam / 200 normal.

Порядок — 3 Unicode code points, additive smoothing `alpha=1`. Алфавит общий для классов,
строится только по train и содержит дополнительный unknown bucket. Переходы не пересекают
границы сообщений. Для каждого класса считается средний log likelihood по переходам,
затем `markovScore = sigmoid(avgLL_spam - avgLL_normal)`. Это дополнительный сигнал,
а не откалиброванная вероятность спама. Для текста длиной до трёх символов оценки нет;
полностью неизвестные контексты дают нейтральный 0.5.

LR обучается независимо, Markov не добавляется в её тренировочные признаки: нет обучения
классификатора на оценке Markov, уже видевшего собственную метку этого примера.
Алфавит и обе таблицы переходов используют только train после группировки дубликатов.
Validation оценивает базовую комбинацию LR + Markov (до контекстных сигналов этапа 5):
`finalScore = 0.9 * classifierScore + 0.1 * markovScore`. Если Markov не дал оценку,
используется classifierScore. Если отсутствует оценка классификатора, Markov самостоятельно
не принимает решение. Веса фиксированы версией формата; порог ASK_ADMIN остаётся 0.60.

Карточка показывает классификатор, Markov и итог отдельно. `/spam stats` указывает наличие
Markov; validation-метрики относятся к базовому score. Миграция SQLite 3 → 4 добавляет
`predictions.markov_score` и `final_score`. Для прежних прогнозов Markov остаётся NULL,
final_score заполняется прежним classifier_score. Предсказания не становятся обучающими метками.

Markov-таблицы хранятся в JSON вместе с LR и заменяются атомарно как одна модель. Они содержат
фрагменты текста: на них распространяются правила доступа к модели и резервным копиям.
Лимиты — 8192 символа алфавита и 200000 различных переходов суммарно. Превышение лимитов,
ошибка обучения или некорректный артефакт отклоняют обновление, сохраняя предыдущую модель.
Автоматические удаления не включаются.

## Очистка служебных сообщений

После выбора Spam / Normal / Пропустить итоговая карточка и команда `/spam review`
удаляются через 15 секунд. Пока проверка ожидает решения, таймер не запускается.
Автоматические карточки также удаляются через 15 секунд после решения. Если администратор
нажимает кнопку устаревшей/истёкшей карточки, она тоже ставится на очистку.
Проверяемое сообщение не входит в эту очистку: Normal/Skip оставляют его в чате,
Spam удаляет его прежним отдельным действием. Разметка и аудит сохраняются в SQLite.

Ответы и команды `/spam status`, `/spam stats`, `/spam train`, `/spam undo`, подсказки
и ошибки антиспама очищаются через 15 секунд после ответа. Для обучения отсчёт начинается
после результата, а не при запуске worker. Миграция 4 → 5 сохраняет ID команды в проверке:
ожидающее ревью можно завершить после перезапуска с очисткой связанной команды.

Для остальных служебных slash-команд в группах также удаляются команда и её текстовые ответы:
`/arm_help`, `/help`, `/pool`, `/stats`, `/top`, `/lef_top`, `/snake_top`, `/retag`,
`/addstickerpack`, `/addultrastickerpack`, `/addgif`, `/addultragif`, `/mute`, `/ban`.
Отсчёт — после завершения обработчика. Посторонние сообщения и результаты развлекательных
действий не включаются в очистку. Команды, адресованные другому боту, не включаются.

Таймеры работают в памяти и отменяются при остановке процесса: уже назначенная очистка
не восстанавливается после перезапуска. Если Telegram отказал в удалении (например, нет
прав), сообщение останется; ошибки очистки не отменяют модерацию и не создают новых сообщений
в чате. ID решения для `/spam undo` виден в итоговой карточке до её удаления.

## Similarity, кампании и поведение: этап 5

Работает на TypeScript с существующей активной моделью формата 1/2/3, без переобучения.
При COLD_START собираются наблюдения, но автоматические предложения по-прежнему ждут
первую модель. Новые данные начинают собираться после обновления: старая таблица сообщений
не превращается задним числом в историю активности, поскольку содержит и ручные проверки.
Миграция SQLite 5 → 6 выполняется при запуске и сохраняет прежние данные.

**Similarity.** Косинусное сходство char TF-IDF по замороженным vocabulary/IDF активной модели.
Для каждой группы выбираются до 200 последних уникальных подтверждённых примеров обоих
классов в пределах срока хранения. Учитываются ADMIN_CONFIRMED, ADMIN_REJECTED и BOOTSTRAP;
противоречивые метки и все редакции проверяемого сообщения исключены. Undo сразу исключает
соответствующую метку. Хранятся максимумы spam/normal и ID примеров. При сходстве spam ≥ 0.95
и превосходстве над normal больше 0.02 добавляется сигнал. Сходство normal не создаёт белый
список и не отменяет оценку классификатора. Короткие тексты (<12 UTF-16 единиц), длинные (>4096),
векторы с <10 известными n-граммами и тексты с покрытием словарём <50% не сравниваются.

**Кампании.** Текущее сообщение сравнивается с актуальными версиями сообщений той же группы,
активными за последние 10 минут. Косинус ≥ 0.90 объединяет их вокруг текущего сообщения;
это локальная группа похожих сообщений, а не транзитивный кластер всех пересылок.
Считаются разные авторы, включая текущего: 2 → 0.3, 3–4 → 0.6, 5+ → 1. Один автор
и его редакции не увеличивают число участников. В предсказании сохраняются ID совпадений.
Совпадение шаблона — повод проверить, а не доказательство спама.

**Поведение.** Отдельная таблица `observed_messages` хранит одну запись на Telegram-сообщение.
Повтор update и редакция не увеличивают счётчик отправленных сообщений. Считаются наблюдённые
текстовые сообщения/подписи пользователя за 60 секунд и 10 минут, число наблюдений за срок
хранения, его нормализованные дубликаты за час и другие авторы с той же ссылкой за час.
Технические slash-команды и ручной `/spam review` не добавляют активность; отредактированный
текст со slash-префиксом остаётся проверяемым содержимым. Медиа без подписи не входят в счётчики.
«Первое наблюдённое» означает первое в доступной истории бота, а не первое сообщение человека
за всё время. События `new_chat_members` сохраняют время вступления; без такого события
время и количество сообщений после вступления — NULL. Повторный вход начинает новый отсчёт.

Ссылки сравниваются по настоящему URL, включая скрытые `text_link`, с сохранением path/query.
Разные адреса не отождествляются по `<URL>`. Fragment удаляется; редиректы и внешние страницы
не запрашиваются. До 32 адресов из сообщения. Эвристика поведения: первое наблюдение +0.15,
вступление менее минуты назад +0.15, наличие URL +0.2, такой URL у другого автора +0.3,
более трёх сообщений за минуту +0.2; сумма ограничена 1. Дубликаты за час и частота за 10 минут
пока сохраняются для анализа, без отдельного веса.

**Решение и аудит.** Политика версии 1:
`priority = base + (1 - base) * (0.2 * similarityFlag + 0.15 * campaignScore + 0.1 * behaviorScore)`.
`base` — прежняя комбинация LR + Markov. Без валидного base новый приоритет не появляется.
Порог ASK_ADMIN остаётся 0.60; проверка администраторов, cooldown и лимит очереди сохраняются.
`predictions.final_score` у новых прогнозов содержит приоритет; `classifier_score` и
`markov_score` сохраняют отдельные оценки. `prediction_signals` атомарно хранит версию политики
и объясняющий JSON рядом с предсказанием. У прежних прогнозов этой записи нет, и их final_score
имеет прежний смысл. Карточка показывает составляющие; итог не называется вероятностью.
Validation и обучение LR/Markov не используют онлайн-историю: опубликованные метрики
не оценивают качество этих эвристик. Автоматические оценки не создают метки для обучения.

Контекст ограничен 500 последними сообщениями за час, поэтому в очень активных группах
кампании, дубликаты и совпадения URL могут недосчитываться. Счётчики частоты считаются отдельно
по индексам без этого ограничения. Кэш векторов ограничен 512 текстами и 200000 компонентами
на экземпляр модели. Наблюдения и вступления переживают перезапуск и удаляются согласно
сроку хранения; объяснения удаляются каскадно с предсказаниями. Всё изолировано по chat_id.
Автоматических удалений, банов и мутов на основании новых сигналов нет.

## SHADOW, метрики и управление моделью: этап 6

Команды доступны только действующему администратору от личного аккаунта:

```text
/spam mode SHADOW
/spam mode LEARNING
/spam models
/spam metrics [version]
/spam calibrate [version]
/spam threshold <version> <порог>
/spam rollback <version>
```

`SHADOW` сохраняет обычные оценки, контекст и решение ALLOW/ASK_ADMIN, но не создаёт
автоматические карточки и не расходует cooldown предложений. ASK_ADMIN здесь означает
«бот предложил бы проверку». `/spam review` и решения по уже существующим карточкам остаются
ручными действиями администратора. Другие развлекательные/модераторские команды бота режим
не отключает. Возврат в LEARNING включает предложения только для новых прогнозов, без
отправки накопленного SHADOW-задним числом. Новые и существующие группы по умолчанию сохраняют
LEARNING; SHADOW включается явно. Без обученной модели сохраняется COLD_START.

Миграция SQLite 6 → 7 добавляет `spam_modes`, `model_thresholds`, `prediction_policy` и
`model_audit`. Настройки переживают перезапуск. Режим принадлежит группе, порог — версии
модели. Каждый новый прогноз атомарно сохраняет режим, действовавший порог и версию контекстной
политики. Прежним прогнозам эти параметры задним числом не приписываются.

`/spam models` показывает последние 20 версий, даты обучения, активность и сохранённые пороги.
Артефакты остаются неизменными. `/spam rollback <version>` проверяет принадлежность группе
и валидность артефакта, затем атомарно переключает активную версию. Порог выбранной версии
восстанавливается (если не менялся — 0.60), режим группы сохраняется. Кэш inference обновляется
без перезапуска. Чужая, отсутствующая или повреждённая версия не меняет активную модель.
История прогнозов и разметка сохраняются. Уже созданные карточки не пересчитываются.
Если настройки/версия были изменены во время обучения, поздний результат worker отклоняется,
чтобы не перезаписать решение администратора. Обучение новой версии сохраняет режим группы
и начинает её порог с 0.60. Административные операции и активации записываются в аудит.

`/spam metrics [version]` показывает TP/FP/TN/FN, precision, recall, F1 и FPR отдельно для
SHADOW/LEARNING при текущем пороге версии, общий пересчёт и оценку по историческим порогам
до cooldown. Нулевой знаменатель отображается как отсутствие оценки, а не нулевая точность.
Берутся последние 30 дней, максимум 10000 свежих прогнозов данной версии до фильтрации,
только с сохранённой политикой контекста 1 и валидным score. Защищённые авторы исключены.
Для качества используются только ADMIN_CONFIRMED/ADMIN_REJECTED, записанные не раньше прогноза.
Неразмеченные, Skip, Bootstrap и автоматические оценки не становятся ground truth.
Undo немедленно исключает метку. Train/validation-хэши и их известные reduced-дубликаты
исключаются; внутри оценки выбирается один самый ранний прогноз на reduced-текст, конфликты
меток исключаются. Оценки разных моделей не объединяются.

Эти метрики описывают размеченную выборку, а не весь чат. Администраторы чаще проверяют
подозрительные сообщения: precision/recall/FPR такой выборки могут быть смещены. Для оценки
в SHADOW вручную проверяйте также обычные сообщения, выбранные независимо от score.
Случайная автоматическая выборка и доверительные интервалы в этом этапе не реализованы.
Изменение порога не меняет сохранённые прогнозы и старые validation-метрики базовой модели.

`/spam calibrate` выполняет подбор порога итогового приоритета, а не калибровку вероятностей.
Уникальные размеченные группы сортируются по порядку прогнозов: первые 60% — calibration,
поздние 40% — holdout. В каждой части нужны минимум 10 spam и 10 normal. Перебираются пороги
0.05–1.00 с шагом 0.01. На calibration выбирается максимальный recall среди порогов с
precision ≥95% и минимум 10 положительными прогнозами; при равенстве — больший порог.
Holdout не участвует в выборе. На нём выбранный порог должен снова дать precision ≥95%
и минимум 10 положительных прогнозов. Иначе применение не рекомендуется; другой порог
по holdout автоматически не ищется. Эти критерии — точечные оценки на ограниченной выборке,
они не гарантируют 95% precision в будущем. Повторные ручные эксперименты на том же holdout
не являются независимыми подтверждениями качества.

Результат с размерами частей, метриками и ID использованных прогнозов записывается в аудит.
Порог никогда не применяется автоматически: администратор явно отправляет
`/spam threshold <version> <порог>` (диапазон 0.05–1). Команда требует указанную активную версию,
поэтому рекомендация старой модели не применяется случайно к новой. Недостаток данных,
отсутствие подходящего порога или ошибка расчёта сохраняют прежние настройки.
В LEARNING и SHADOW автоматическое удаление не включается. ACTIVE описан ниже.

## ACTIVE: этап 7

Допуск к удалению намеренно отделён от `/spam calibrate` и старых validation-метрик.
По умолчанию ничего не удаляется. `/spam mode ACTIVE` не включает режим: нужен следующий
порядок действий от личного аккаунта действующего администратора этой группы:

```text
/spam threshold <version> 0.95
/spam active prepare <version>
/spam active sample <id проверки>
/spam active check <id проверки>
/spam active enable <id проверки>
```

Порог выбирается администратором до проверки; нижний допустимый порог ACTIVE — 0.90.
`prepare` переключает группу в SHADOW и открывает новую перспективную контрольную выборку.
В неё попадают следующие 1000 уникальных по reduced-тексту пригодных прогнозов, независимо
от score. Train/validation-хэши и известные reduced-дубликаты, защищённые авторы, отсутствие
оценки исключаются. Это последовательная выборка потока, а не выбор только подозрительных
сообщений. Её состав фиксируется до разметки; старая выбранная вручную выборка не даёт допуск.
Новая проверка аннулирует предыдущую.

`sample` выдаёт следующий неразмеченный пример без показа score. Используются обычные
кнопки Spam/Normal; Spam остаётся явным ручным удалением. Все 1000 примеров должны получить
человеческую метку: Skip и отсутствие метки не считаются Normal и блокируют допуск. Если
проверяемая редакция уже устарела или карточка истекла и её нельзя завершить, начинайте новую
проверку. Недоступные примеры не выбрасываются ради улучшения результата.

`check` проверяет одновременно:

- precision ≥99% и FPR ≤1% при зафиксированном пороге;
- минимум 100 положительных прогнозов и 400 подтверждённых normal;
- все 1000 независимых по reduced-тексту примеров размечены после прогноза;
- та же активная версия, тот же артефакт, порог и контекстная политика 1;
- контрольная проверка не старше 30 дней.

Проверка сохраняет fingerprint данных и метрики. Успешный check **не включает** удаление.
Только `enable` повторно проверяет данные и права администратора/бота и выдаёт допуск на 7 дней.
Это точечные оценки на наблюдаемом потоке, не гарантия будущего качества и не доверительный
интервал. При малой доле спама в выборке может не набраться 100 положительных прогнозов:
ACTIVE в таком случае остаётся недоступен, критерии автоматически не ослабляются.

В ACTIVE удаляются только сообщения выше проверенного порога. Лимит — одна попытка удаления
в минуту на группу; превышение оставляет остальные сообщения в чате. Автобаны и автомуты
не выполняются. Перед удалением повторно проверяются права бота и включившего ACTIVE
администратора, защита автора (администратор/бот/канал), актуальная редакция, действующий допуск.
Сообщения с уже существующей ручной проверкой или меткой автоматически не удаляются.
Остаётся неизбежный промежуток между последней проверкой и обработкой запроса Telegram;
Bot API не предоставляет удаления с условием «только если редакция не изменилась».

Попытка атомарно резервируется в `active_actions` перед обращением к Telegram. Статусы:
PENDING (в том числе остановка процесса до получения результата), DELETED, FAILED_OR_UNKNOWN.
Повтор update, перезапуск и неопределённый сетевой результат не запускают повторное удаление.
Ошибка удаления переводит группу в SHADOW. Автоматическое удаление не создаёт обучающую метку.

`/spam active log` показывает последние 10 попыток этой группы.
`/spam active review <номер прогноза>` создаёт ручную проверку сохранённого снимка.
Ответ Normal немедленно отзывает ACTIVE как сообщение о ложном срабатывании.
Удалённое сообщение автоматически не восстанавливается; исходный текст сохраняется в SQLite
в пределах retention. Решение остаётся доступным для аудита.

Отключение: `/spam mode SHADOW` (или LEARNING). Смена порога, обучение/активация новой модели
и rollback отзывают допуск; при ранее включённом ACTIVE группа возвращается в SHADOW.
Rollback не восстанавливает прежнее разрешение на удаление. Перед использованием допуска
проверяются его срок, данные, fingerprint артефакта и меток; отмена/изменение метки либо
удаление данных по retention также отключают ACTIVE. Просмотр метрик архивной версии
сам по себе действующий допуск не отзывает. Допуск переживает перезапуск, но все проверки
перед действием выполняются заново; истёкший или изменившийся допуск не используется.

Миграция 7 → 8 сохраняет старые политики и добавляет ACTIVE в снимок политики предсказания,
таблицы контрольных выборок, допусков и попыток удаления. Режим ACTIVE выводится из валидного
допуска, а не из свободно выставляемого флага. Операции prepare/check/enable/отзыв записываются
в `model_audit`. Реальная группа при разработке не переводится в ACTIVE автоматически.
